# CLAUDE.md

Tourist Order (touristorder.com) : site de livraison pour touristes en Israël (Next.js 16 App Router, Prisma 6, PostgreSQL / Supabase, Tailwind 4). Côté client en cinq langues (français, anglais, russe, hébreu, espagnol) ; espace gérant et code métier en français. Voir `README.md` pour le fonctionnement et le déploiement.

## Commandes

```bash
npm run dev          # serveur de développement
npm run typecheck    # tsc
npm run lint         # eslint
npm test             # vitest (tests/)
npx prisma db push   # applique prisma/schema.prisma en local (en production : fait par la mise en ligne, voir ci-dessous)
npm run seed         # catégories + réglages ; seed:demo ajoute des produits d'exemple (jamais en production)
```

## Règles

- **Cinq langues côté client** (`lib/langues.ts` : fr, en, ru, he, es ; l'hébreu se lit de droite à gauche). AUCUN texte en dur dans une page ou un composant côté client : il va dans `lib/i18n/fr.ts` (textes du site, envoyés au navigateur) ou `lib/i18n/serveur/fr.ts` (erreurs, e-mails, messages WhatsApp du gérant, pages légales), puis dans les quatre autres langues — même clé, mêmes `{valeurs}`, mêmes liens (`tests/langues.test.ts` le refuse sinon ; `npx tsx tests/outils/verifier-langue.ts <code>`). Serveur : `traduction()` (`lib/traduction.ts`) → `{ langue, t, ts }` ; navigateur : `useTraduction()` (`components/LangueProvider.tsx`). Nombres : `compter` (le russe a quatre formes), valeurs : `remplir`. Prix, jours, heures : `formatPrix(x, langue)`, `libelleDuJour(jour, undefined, langue)`, `heureLisible`. L'espace gérant reste en français, de gauche à droite (`proxy.ts`, `app/admin/layout.tsx`) ; les fonctions partagées gardent le français par défaut (les tests et l'admin n'ont rien à passer).
- **Une adresse par langue** : le français garde les adresses sans préfixe (`/panier`), les autres langues ont le leur (`/he/panier`). Les pages ne sont PAS dupliquées : `proxy.ts` réécrit `/he/panier` vers `/panier` et pose l'en-tête `x-langue`, que `langueActuelle()` (`lib/traduction.ts`) lit — c'est l'adresse qui donne la langue. Toute la décision est dans `aiguiller` (`lib/langues.ts`, pur, testé) : sans préfixe, un visiteur est redirigé vers l'adresse de sa langue (son choix — cookie `langue`, posé par `changerLangue` SEULEMENT, jamais par `proxy.ts` : en production les liens d'une page sont préchargés en arrière-plan, et une adresse à préfixe préchargée défaisait le choix que le visiteur venait de faire —, sinon son navigateur) ; un moteur de recherche, qui ne demande rien, lit le français ; `/fr/…` revient sans préfixe ; `/admin` est toujours en français ; `/compte/acces` (lien reçu par e-mail) et les fichiers n'ont pas de langue. **Tout lien, toute redirection et tout `router.push` côté client passe par `lien("/chemin")`** (`traduction()` côté serveur, `useTraduction()` dans le navigateur ; `lienPour(langue, chemin)` ailleurs) — jamais un `href="/panier"` en dur : il sortirait le client de sa langue (`parcours-langues.mjs` le refuse). Un lien envoyé au client (e-mail, message WhatsApp de l'admin) porte le préfixe de SA langue (`prefixeDe`). `usePathname()` rend l'adresse AVEC son préfixe : la retirer avec `langueDuChemin`. Changer de langue = `router.replace` vers la même page à l'autre adresse ; `LangueProvider` redemande la page au serveur quand l'adresse et la langue rendue ne s'accordent plus (l'en-tête et le pied suivent). Référencement : `adressesParLangue(chemin, langue)` donne l'adresse de référence et les équivalents (« hreflang ») de chaque page publique ; `app/sitemap.ts` et `app/robots.ts` couvrent les cinq langues.
- Hébreu : marges et positions « logiques » seulement côté client (`ms-`, `me-`, `ps-`, `pe-`, `start-`, `end-`, `text-start` ; jamais `ml-`, `pl-`, `left-`, `text-left`), une flèche se retourne avec `rtl:rotate-180`, un texte venu de la base (nom d'article, adresse, note) est dans `<bdi>`, un téléphone ou un e-mail a `dir="ltr"`. Un élément placé hors de l'écran l'est du côté `start` (à gauche, il élargirait la page en hébreu).
- Le gérant répond aux clients en **français, en anglais ou en hébreu** (sa décision, 12 novembre 2026) : ces trois sites annoncent un service dans la langue du client (`accueil.surtitre`), et la page de contact dit partout dans quelles langues on répond. Le russe et l'espagnol ne sont JAMAIS promis (`tests/langues.test.ts`) : ces deux sites disent « nous répondons en anglais, en hébreu ou en français ». Les rayons, le message d'accueil et les modes de paiement de départ sont traduits tant que le gérant ne les a pas changés (`nomDuRayon`, `libelleDuMode`, `MESSAGE_ACCUEIL_PAR_DEFAUT`).
- **Catalogue traduit** : `lib/i18n/catalogue/<langue>.ts` va du texte FRANÇAIS de départ (`prisma/*.ts`) à sa traduction — noms et descriptions d'articles, noms et choix d'options, villes, noms des tarifs. La base ne change pas : elle reste en français, la traduction se fait à l'affichage, côté serveur (`nomArticle`, `descriptionArticle`, `libelleOptions`, `nomVille`, `nomTarif`, `traduireGroupes` dans `lib/i18n/catalogue`). Un texte que le gérant a écrit ou modifié dans l'admin n'est pas dans la table : il s'affiche tel quel. Ces tables sont LOURDES : jamais importées par un composant du navigateur (`"use client"`) — le serveur envoie le résultat (lectures de `lib/catalogue.ts` avec la langue ; `affichage` de la page du panier). Les lignes d'une commande, l'admin, la liste de courses et les exports gardent le français. Options : ce qui est choisi, envoyé et vérifié reste `nom` / `libelle` du gérant ; `affiche` n'est que ce que le client lit (`libelleAffiche`). Recherche : `rechercher(q, langue)` cherche aussi dans les traductions (`chercherDansLaLangue`). **Ajouter un article, une description, une option ou une ville dans `prisma/*.ts` = ajouter sa traduction dans les quatre fichiers** (`tests/catalogue-langues.test.ts` le refuse sinon) : mêmes chiffres que le français, marques inchangées, rien d'ajouté à ce que dit le texte (casher, sans gluten… traduits tels quels).
- **Adresse obligatoire avant la commande** : nom, téléphone, e-mail, ville, où le client loge (`logement` : `APPARTEMENT`, `MAISON` ou `HOTEL` — `lib/adresse.ts`) et la rue ou le nom de l'hôtel (`adresse`) sont exigés par `schemasPour` (`lib/validation.ts`) — rien n'est enregistré ni à payer sans eux. `etage` et `appartement` ne sont exigés que pour un appartement ; une maison n'en a pas ; à l'hôtel le numéro de chambre est facultatif (rangé dans `appartement`) ; `codeEntree` est facultatif. **À l'hôtel, on ne monte pas dans les chambres** (décision du gérant, 12 novembre 2026) : on appelle le client et il descend chercher sa commande — dit au client dès qu'il choisit « Hôtel » (`panier.hotelAvis`), dans les conditions de vente, sur son suivi et dans son e-mail (`adresse.remiseHotel`), dans les messages « en route » et « j'arrive » du gérant (`messages.hotel`), et au livreur (« Ne pas monter », `LIBELLES_ADRESSE_FR`). Une commande d'avant ce choix (`logement` vide) s'affiche comme un appartement. `Commande.adresse` ne porte que la rue ou l'hôtel (Waze) : l'adresse entière s'affiche avec `adresseComplete` / `precisionsAdresse` (`lib/adresse.ts`). `Commande.langue` = la langue du client : son e-mail (`langueDuCourriel`) et les messages WhatsApp du gérant (`langueDesMessages`) sont écrits dans cette langue.
- **Référence de commande** : le client ne lit JAMAIS « n°1 » — le site doit avoir l'air d'une maison installée (demande du gérant, 12 novembre 2026). Partout côté client (suivi, compte, « Mes commandes », e-mails, reçu, messages WhatsApp dans les deux sens) : `referenceDeCommande(numero, nomClient)` (`lib/reference.ts`, pur) → « BC-58100 » = les initiales du client, deux chiffres qui ne comptent pas, puis le numéro écrit à l'envers (100 → 001 → n°1). Les dictionnaires portent `{reference}`, jamais `{numero}` (`tests/reference.test.ts`), et le navigateur ne reçoit pas le numéro (`mesCommandes`). Le gérant voit toujours le numéro ET la référence (liste, commande, e-mail, Telegram) et retrouve une commande par l'un ou l'autre (`numeroDepuisReference`, champ « Retrouver une commande » de `/admin`). Ne pas changer la formule : les références déjà données aux clients ne se reliraient plus.
- Montants en **agorot** (Int). Calcul unique : `lib/calcul.ts`. Le serveur recalcule depuis la base (`lib/commandes.ts`).
- `exigerAdmin()` en tête de chaque page et action de `app/admin/(protege)`.
- Pages publiques : produits lus via `PRODUIT_PUBLIC` (`lib/catalogue.ts`) — jamais `prixAchat`, `boutique`, `lienWolt`.
- Apparence (côté client) : sobre — encre (`bg-encre`), blanc, traits fins, gris neutres (les classes `slate-*` sont remappées dans `@theme`), un seul accent (`marque`, pour les liens et le focus). **Aucun emoji côté client** : icônes au trait de `lucide-react` (`IconeRayon` pour un rayon, d'après son adresse). Un article est une ligne de menu (`CarteProduit`) : nom, format, prix — la photo seulement s'il y en a une, jamais d'image de remplacement. Avec une photo (96 px), elle est à GAUCHE de la ligne et le bouton « + » est posé dans son coin haut gauche, DANS TOUTES LES LANGUES — en hébreu aussi, où le reste de la page se retourne (`rtl:flex-row-reverse`, `left-0` : la seule exception à la règle des positions logiques, décidée par le gérant le 12 novembre 2026, « comme sur Wolt »). Couleurs du site : fond `encre`, « + » blanc, et « − n + » à la même place une fois l'article au panier. Sans photo, le bouton reste en bas à droite. Arrondis et graisses se règlent dans `@theme` (`--radius-*`, `--font-weight-*`), pas classe par classe. Logo : le sigle (un T et un O plein couleur `soleil` dans une tuile encre) a UN tracé, `lib/sigle.ts`, rendu par `components/Sigle.tsx` (SVG sans classe ni police : il sert aussi aux images générées) ; le jaune `soleil` est réservé à ce O. L'icône de l'onglet et la carte d'aperçu de lien sont générées avec lui (`app/icon.tsx`, `app/apple-icon.tsx`, et `app/apercu/[langue]/route.tsx` : une carte par langue, textes dans `meta.apercu` de `lib/i18n/serveur/` ; polices dans `assets/polices/` — Geist pour le latin et le cyrillique, Heebo pour l'hébreu, dont les lignes sont données retournées car l'outil n'écrit que de gauche à droite), et les fichiers de `public/logo/` portent le même tracé (`tests/logo.test.ts`) : changer le dessin = changer `lib/sigle.ts` ET refaire ces fichiers.
- Menu du gérant (`components/admin/NavAdmin.tsx`) : chaque lien doit rester atteignable. Il passe à la ligne à partir de `sm` ; sur téléphone c'est une rangée qui défile (bord droit estompé, lien actif amené à l'écran). Ajouter un lien = relancer `tests/navigateur/menu-gerant.mjs` : une rangée `rail` cache sa barre de défilement, un lien de trop sort de l'écran sans que rien ne le signale.
- Classes CSS maison = `@utility` dans `app/globals.css` (pas `@layer components` : sorti de sa couche par le chargeur Turbopack, il écrasait les utilitaires).
- Formulaire non contrôlé + `useActionState` : React le vide après l'action et un `<select>` perd sa valeur → reconstruire le formulaire (`key`) avec les valeurs renvoyées (voir `FormulaireProduit.tsx`), ou utiliser des champs contrôlés (`PageDuPanier.tsx`).
- Le site **vouvoie** le client (pages, e-mails, messages WhatsApp envoyés au client ; dans les autres langues : forme polie — « вы », « usted », pluriel neutre en hébreu) ; l'espace gérant tutoie le gérant. `tests/paiement.test.ts`, `tests/logique.test.ts` et le parcours `parcours-paiement.mjs` refusent un tutoiement côté client.
- **Paiement à la commande**, avant les achats sur Wolt : une seule définition, `lib/paiement.ts` (pur) — `etatDuPaiement` (à payer, payée, complément, à rembourser, rien), `estReglee`. `Commande.montantPaye` / `payeLe` ; « Paiement reçu », « Complément reçu » et « Remboursement fait » sont le même geste (`solderCommande` : reçu = dû). Seule une commande réglée entre dans la liste Wolt et passe « commandée sur Wolt » en lot. Les coordonnées de paiement (`Reglages.coordonneesPaiement`) et le jeton Telegram sont privés : jamais dans `reglagesPublics`, `infosLegales`, une page publique ni un e-mail — ils ne partent que dans le message WhatsApp du gérant (`messagePourLeClient`). Seule exception, voulue par le gérant (12 novembre 2026) : `Reglages.lienBit`, son lien de paiement Bit (https seulement, `lienDePaiementValide`) — montré sur la page de suivi et nulle part ailleurs (bouton « Payer avec Bit », avec le montant et la référence à indiquer), au seul client qui a choisi Bit (`paieParBit`) et tant qu'il reste à régler, et ajouté à ce même message WhatsApp ; jamais dans `reglagesPublics`, une autre page ni un e-mail (`tests/paiement.test.ts`). Un seul gros bouton WhatsApp à la fois, sur le suivi comme dans la commande du gérant : quand le paiement a le sien, « nous écrire » n'est qu'un lien.
- Demande d'article hors catalogue : `Commande.demandeLibre` ; un panier vide n'est une commande qu'avec une demande (`commandeSchema`). Le gérant ajoute l'article avec `ajouterLigneLibre` (ligne sans `produitId`), qui recalcule le total comme `modifierLigne` (`recalculer`).
- Exports comptables : `lib/export.ts` (pur) — toute cellule passe par `cellule` (formules neutralisées). La route `/admin/export/[type]` appelle `exigerAdmin()` elle-même : un layout ne protège pas une route.
- Alerte Telegram : `lib/telegram.ts` — ne lève jamais, ne journalise jamais le jeton. Ses actions reviennent sur `#telegram` avec leur message (`tgOk` / `tgErreur`) : le résultat s'affiche dans la partie Telegram, pas en haut de la page. `TELEGRAM_API` ne sert qu'au parcours `parcours-telegram.mjs` (faux Telegram local).
- Une valeur par défaut qui change (modes de paiement, message d'accueil, description d'un article de départ) : la mise en ligne ne remplace que les valeurs restées à l'ancien défaut (`mettreLesReglagesANiveau`, `prisma/remplissage.ts`), jamais ce que le gérant a modifié.
- Jours = jours israéliens (`lib/dates.ts`), stockés `AAAA-MM-JJ`.
- Options produit (variantes) : `lib/options.ts` seulement — saisie admin, clé de panier, validation et supplément côté serveur.
- Mobile : une case `sr-only` reste dans un parent `relative` (sinon, dans une rangée qui défile, elle élargit la page), et `fieldset { min-inline-size: 0 }`. Une grille à une colonne s'écrit `grid grid-cols-1` (colonne `minmax(0,1fr)`) : sans cela un texte `truncate` (nom d'article long) élargit la page. Vérifier la largeur avec `innerWidth <= screen.width` : une page trop large se dézoome et `scrollWidth === innerWidth` ne voit rien.
- Un produit à `prix = 0` est « à définir » : jamais visible ni commandable (`VISIBLE` dans `lib/catalogue.ts`, `creerCommande`), jamais en ligne (`produitSchema`, `basculerProduit`).
- Tarifs selon le moment : `lib/tarifs.ts` seulement (pur, partagé panier/serveur). Le moment = jour + début du créneau ; la commande copie `tarifNom`, `majorationPct`, et les frais (`tarif*`) pour les recalculs.
- Villes livrées : table `Ville` ; livraison = `fraisDeLivraison` (`lib/villes.ts`, pur, partagé) = tarif du moment + supplément de la ville (+ express). Le minimum = le plus élevé (général, ville). La commande copie `supplementVille`.
- Jours et créneaux proposés : `joursDeLivraison(reglages)` (`lib/creneaux.ts`, pur) — jours livrés ; le jour même seulement avant `heureLimite` et pour les créneaux qui commencent après maintenant + `delaiPreparation`. Avec une limite (`Reglages.commandesParCreneau`), un créneau plein est dans `complets` (affiché, non choisissable). Les pages et `creerCommande` passent par `joursOuverts` (`lib/livraisons.ts`), qui compte les commandes non annulées : jamais `joursDeLivraison` directement côté serveur.
- Connexion admin : seuls les échecs comptent (`bloque` / `noterEchec`, `lib/limite.ts`). Utilisé par le panier ET par `creerCommande`.
- La base du catalogue est `prisma/catalogue.ts` (articles « à compléter », sans prix : n'y mettre aucun prix). Les articles réels de Wolt Market, avec leur prix, sont dans `prisma/articles-wolt.ts` (prix normal de Wolt, jamais le prix promo ; nom français pour le client, `nomWolt` en hébreu pour le gérant). Chaque relevé de boutique est un LOT (`LOTS_WOLT` dans `prisma/remplissage.ts` : Wolt Market, Dynamica dans `prisma/articles-dynamica.ts`…), installé UNE SEULE FOIS (`installerLesArticlesWolt` : dès qu'un article du lot existe, reconnu à son `nomWolt`, ce lot n'est plus touché ; un nouveau lot s'ajoute sans toucher aux autres) — ensuite les prix se gèrent dans l'admin ; ne jamais écraser un prix posé par le gérant. Un lot ajouté plus tard à une boutique déjà installée (les fiches du 11 novembre, `prisma/articles-wolt-fiches.ts`) ne reprend AUCUN `nomWolt` d'un autre lot (sinon il passerait pour déjà installé) et porte un `ordre` de départ élevé : ses articles se rangent après ceux du rayon. Descriptions écrites d'après les fiches de Wolt : seulement ce que la fiche montre (texte, étiquettes « casher », « sans gluten »…, emballage), première phrase courte (la liste n'en montre qu'une ligne) ; pour enrichir la description d'un article déjà installé, une ligne `{ nomWolt, ancienne, nouvelle }` dans `DESCRIPTIONS_ENRICHIES` — elle n'est posée que si la description est restée celle de départ. `npm run seed:demo` est le jeu de test (base entière + 18 prix inventés, sans les articles Wolt) : les parcours navigateur en dépendent.
- `Produit.nomWolt` est réservé à l'admin, comme `prixAchat`, `boutique`, `lienWolt`, `prixIndicatif` : jamais dans `PRODUIT_PUBLIC`.
- Relevé de prix d'après les captures Wolt du gérant : un fichier par relevé (`prisma/releve-wolt-1112.ts`) — prix NORMAUX (le prix barré quand Wolt affiche une promotion), `ancien` = le prix que le code avait posé (relevé précédent ou liste du gérant). `appliquerLeReleveDePrix` l'applique une seule fois (`operationsFaites`) ; `changementsDuReleve` (pur) ne remplace jamais un prix que le gérant a changé lui-même, met le prix d'achat au prix de Wolt (l'article sort de « Prix à vérifier ») et note le `nomWolt` manquant. Un article que Wolt vend sous une autre marque ou un autre format n'est pas rapproché d'office : on le signale au gérant. Les articles ajoutés à cette occasion forment un lot à part de `LOTS_WOLT`, avec leurs traductions dans `lib/i18n/catalogue`. Pour lire ses captures : un PDF d'une page entière se convertit en image (`pdftoppm -r 72`) puis se découpe en bandes ; une image collée dans la discussion arrive trop petite pour être lue.
- Articles ajoutés d'après les captures Wolt du gérant (sa demande du 12 novembre : « rajoute-moi des produits ») : `prisma/articles-wolt-captures.ts`, un lot de `LOTS_WOLT` comme les autres (273 articles : poisson, pain, lait et œufs, yaourts et desserts). On y met tout ce que la capture montre sauf ce qui est déjà sur le site (reconnu à son `nomWolt`, même dans un autre rayon), les doublons en promotion et ce qui n'est pas un article ; un article de la LISTE du gérant que la capture montre aussi n'est pas ajouté en double : son prix va dans un relevé (`RELEVES_DE_PRIX`, une clé par relevé : un relevé ajouté plus tard s'applique sans rejouer les précédents). Le poisson se range dans « Poisson » : `rayonsDe` y retrouve le rayon « Boucherie & poisson » sur une base où il porte encore son premier nom, et n'en crée jamais un second. Chaque article ajouté a ses traductions (quatre langues) et sa photo repère.
- Photos repère (photos de Wolt tirées des captures du gérant, pour qu'il sache quoi chercher) : PRIVÉES. Fichiers dans `prive/reperes-wolt` (jamais `public/`), liste dans `lib/reperes-wolt.ts` (`PHOTOS_REPERE` : nom, nom exact sur Wolt, fichier), servies seulement par la route `/admin/repere/[fichier]` qui appelle `exigerAdmin()` et ne lit que les fichiers de la liste ; `next.config.ts` (`outputFileTracingIncludes`) les joint à cette route. `repereWolt(...).photo` donne leur adresse ; elles s'affichent dans « Photos rapides », « Prix rapides », « Ma journée » et la commande. Jamais côté client, jamais comme photo d'un produit : elles appartiennent à Wolt et aux marques (`tests/reperes-wolt.test.ts`). En ajouter : découper la photo de chaque carte dans la capture, contrôler sur une planche que chaque photo est bien celle de l'article, ajouter fichiers et lignes.
- Article de la liste que Wolt vend sous une autre forme : `REMPLACEMENTS_DU_12_NOVEMBRE` (`prisma/releve-wolt-1112.ts`) + `remplacerLesArticles` (une seule fois) — seulement sur décision du gérant, à qui on montre d'abord la liste ; le nouveau nom a ses traductions dans `lib/i18n/catalogue`.
- Repère Wolt (le gérant ne connaît pas tous les articles) : `repereWolt` (`lib/repere-wolt.ts`, côté serveur seulement — il lit le catalogue en hébreu, lourd) donne pour un article son nom en hébreu à chercher sur Wolt — le `nomWolt` relevé (exact), sinon la traduction du nom français (affichée avec la mention « traduction ») — et une recherche d'images (`lib/recherche-image.ts`). `components/admin/RepereWolt.tsx` l'affiche avec un bouton « Copier » dans « Ma journée », la liste de courses d'une commande et « Prix rapides » ; les listes copiées portent aussi l'hébreu. Ne pas y reprendre un produit que le site vend déjà. Par défaut, ne jamais copier `prixIndicatif` dans `prix` ni mettre ces articles en ligne par le code. EXCEPTION décidée par le gérant le 11 novembre 2026, prévenu du risque avec des exemples (« fais-le ») : les 360 articles de CETTE liste — tout sauf l'alcool et la mélatonine (`ARTICLES_MIS_EN_VENTE`) — sont mis en vente au prix de la liste, une seule fois (`mettreEnVenteLaListe`, repère `Reglages.listeEnVenteLe` ; jamais un article qu'il a déjà chiffré, renommé ou remasqué). `prixAchat` reste vide : c'est ce vide qui garde l'article repéré « prix non vérifié » (`lib/prix-indicatif.ts` : onglet « Prix à vérifier » de « Prix rapides », signal dans la liste de courses de « Journée ») jusqu'à ce qu'il note le prix de Wolt. - Clé de session (gérant et clients) : `cleDeSession()` (`lib/cle-session.ts`) seulement — `SESSION_SECRET`, sinon une clé dérivée (HMAC) de `SUPABASE_JWT_SECRET` / `POSTGRES_PASSWORD` posés par l'intégration ; une `SESSION_SECRET` trop courte reste une erreur.
- Photos libres de droits (produits frais sans marque seulement) : fichiers dans `public/produits/frais`, article → fichier dans `prisma/photos-frais.ts`, auteur / licence / source dans `lib/credits-photos.ts` (page `/credits` : l'attribution exigée). Licences acceptées : domaine public, CC0, CC BY, CC BY-SA — jamais la GFDL seule, jamais une photo sans crédit (`tests/photos.test.ts`). Posées une seule fois (`installerLesPhotosFrais`), jamais sur un article qui a déjà une photo.
- Photos produit : allégées dans le navigateur avant l'envoi (`reduirePhoto`, `lib/reduire-photo.ts` : 1 600 px, JPEG), puis revérifiées par le serveur (`lib/image.ts` : type lu dans les octets, 4 Mo au plus). Vercel refuse toute requête de plus de 4,5 Mo : ne jamais remonter `TAILLE_MAX_IMAGE` au-delà.
- **Pas de viande ni de volaille au catalogue** : décision du gérant (11 novembre 2026), la cacherout de la viande est trop délicate à garantir. Les 40 articles concernés (frais, surgelés, charcuterie, plats à base de viande : `prisma/retrait-viande.ts`) sont MASQUÉS une seule fois par `retirerLaViande`, jamais supprimés ; le poisson, le végétarien et la nourriture pour animaux restent. Le rayon « Boucherie & poisson » est devenu « Poisson » (adresse `poisson`). Ne plus ajouter de viande : `tests/retrait-viande.test.ts` le refuse.
- Une opération sur les données qui ne doit se faire qu'une fois (masquer, mettre en vente, installer une liste) : sa clé dans `Reglages.operationsFaites` (`operationFaite` / `noterOperation`, `prisma/remplissage.ts`), posée dans la même transaction. Ce que le gérant change ensuite n'est jamais refait. Les rayons se retrouvent par nom OU par adresse et ne se créent qu'au moment d'installer (`rayonsDe`) : un rayon renommé ne doit pas revenir en double.
- La liste « Dynamica Store » du gérant (`prisma/articles-liste-dynamica.ts`, 148 articles d'électronique jusqu'à 8 299 ₪) est installée « à compléter », masquée, et le RESTE : modèles d'une ou deux générations en arrière, prix et garanties invérifiables. La décision de vendre la liste d'épicerie au prix de la liste ne s'y étend pas ; ne la mettre en vente, même en partie, que sur une demande expresse du gérant qui connaît ces raisons.
- Vérifier une mise en ligne de l'extérieur : chaque page porte `<meta name="version">` = les 7 premiers caractères du commit en service (`VERCEL_GIT_COMMIT_SHA`, `app/layout.tsx`). Une mise en ligne qui échoue laisse l'ancienne version en place sans rien montrer : toujours relire ce repère après un push.
- Pages d'erreur : `app/error.tsx` (propriété `retry` dans cette version de Next, pas `reset`) et `app/not-found.tsx` — jamais de détail technique au visiteur.
- Espace client : `exigerClient()` en tête de chaque page/action de `/compte`, et l'id du client connecté dans chaque `where` (propriété). Jetons `lib/session-client.ts` (usage « lien » ≠ « session » ≠ admin). Connexion : même réponse que le compte existe ou non.
- E-mails : gabarits purs dans `lib/courriels.ts` (tout texte externe via `echapper`), envoi `lib/courriel.ts` (Resend, ne lève jamais, `after()`), en dev écrits dans `.courriels/`. Ce qui part chez Resend : `corpsPourResend` (pur, testé) ; `EMAIL_REPONSE` (facultative) devient l'en-tête de réponse. Le bandeau porte le logo (`adresseDuLogo(site)` → une image de `public/logo`, facultative) ; le nom reste du texte. Montants : `lignesDeMontants` (`lib/montants.ts`).
- Un client connecté commande avec l'e-mail de son compte ; le profil d'un compte n'est mis à jour par une commande que si c'est ce client qui est connecté.
- Production (Vercel + Supabase créée depuis Vercel) : l'adresse de la base et les clés Supabase se lisent par `lib/adresses-base.ts` seulement (`DATABASE_URL`, sinon `POSTGRES_PRISMA_URL` posée par l'intégration ; jamais `process.env.DATABASE_URL` ailleurs). `npm run build` lance `prisma/preparer.ts` : pour un déploiement de production seulement (`VERCEL_ENV=production`), `db push` sans `--accept-data-loss`, RLS sur toutes les tables (`prisma/rls.sql`), catalogue de départ sur une base neuve seulement, dossier de photos. Un changement de schéma qui perd des données arrête donc la mise en ligne : le faire à la main, en connaissance de cause.
