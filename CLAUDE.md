# CLAUDE.md

Tourist Order (touristorder.com) : site de livraison pour touristes en Israël (Next.js 16 App Router, Prisma 6, PostgreSQL / Supabase, Tailwind 4). Côté client en cinq langues (français, anglais, russe, hébreu, espagnol) ; espace gérant et code métier en français. Voir `README.md` pour le fonctionnement et le déploiement.

## Commandes

```bash
npm run dev          # serveur de développement
npm run typecheck    # tsc
npm run lint         # eslint
npm test             # vitest (tests/)
npx prisma db push   # applique prisma/schema.prisma en local (en production : fait par la mise en ligne, voir ci-dessous)
npm run seed         # catégories + réglages ; seed:demo ajoute des produits d'exemple (jamais en production)
```

## Règles

- **Cinq langues côté client** (`lib/langues.ts` : fr, en, ru, he, es ; l'hébreu se lit de droite à gauche). AUCUN texte en dur dans une page ou un composant côté client : il va dans `lib/i18n/fr.ts` (textes du site, envoyés au navigateur) ou `lib/i18n/serveur/fr.ts` (erreurs, e-mails, messages WhatsApp du gérant, pages légales), puis dans les quatre autres langues — même clé, mêmes `{valeurs}`, mêmes liens (`tests/langues.test.ts` le refuse sinon ; `npx tsx tests/outils/verifier-langue.ts <code>`). Serveur : `traduction()` (`lib/traduction.ts`) → `{ langue, t, ts }` ; navigateur : `useTraduction()` (`components/LangueProvider.tsx`). Nombres : `compter` (le russe a quatre formes), valeurs : `remplir`. Prix, jours, heures : `formatPrix(x, langue)`, `libelleDuJour(jour, undefined, langue)`, `heureLisible`. L'espace gérant reste en français, de gauche à droite (`proxy.ts`, `app/admin/layout.tsx`) ; les fonctions partagées gardent le français par défaut (les tests et l'admin n'ont rien à passer).
- **Une adresse par langue** : le français garde les adresses sans préfixe (`/panier`), les autres langues ont le leur (`/he/panier`). Les pages ne sont PAS dupliquées : `proxy.ts` réécrit `/he/panier` vers `/panier` et pose l'en-tête `x-langue`, que `langueActuelle()` (`lib/traduction.ts`) lit — c'est l'adresse qui donne la langue. Toute la décision est dans `aiguiller` (`lib/langues.ts`, pur, testé) : sans préfixe, un visiteur est redirigé vers l'adresse de sa langue (son choix — cookie `langue`, posé par `changerLangue` SEULEMENT, jamais par `proxy.ts` : en production les liens d'une page sont préchargés en arrière-plan, et une adresse à préfixe préchargée défaisait le choix que le visiteur venait de faire —, sinon son navigateur) ; un moteur de recherche, qui ne demande rien, lit le français ; `/fr/…` revient sans préfixe ; `/admin` est toujours en français ; `/compte/acces` (lien reçu par e-mail) et les fichiers n'ont pas de langue. **Tout lien, toute redirection et tout `router.push` côté client passe par `lien("/chemin")`** (`traduction()` côté serveur, `useTraduction()` dans le navigateur ; `lienPour(langue, chemin)` ailleurs) — jamais un `href="/panier"` en dur : il sortirait le client de sa langue (`parcours-langues.mjs` le refuse). Un lien envoyé au client (e-mail, message WhatsApp de l'admin) porte le préfixe de SA langue (`prefixeDe`). `usePathname()` rend l'adresse AVEC son préfixe : la retirer avec `langueDuChemin`. Changer de langue = `router.replace` vers la même page à l'autre adresse ; `LangueProvider` redemande la page au serveur quand l'adresse et la langue rendue ne s'accordent plus (l'en-tête et le pied suivent). Référencement : `adressesParLangue(chemin, langue)` donne l'adresse de référence et les équivalents (« hreflang ») de chaque page publique ; `app/sitemap.ts` et `app/robots.ts` couvrent les cinq langues.
- Hébreu : marges et positions « logiques » seulement côté client (`ms-`, `me-`, `ps-`, `pe-`, `start-`, `end-`, `text-start` ; jamais `ml-`, `pl-`, `left-`, `text-left`), une flèche se retourne avec `rtl:rotate-180`, un texte venu de la base (nom d'article, adresse, note) est dans `<bdi>`, un téléphone ou un e-mail a `dir="ltr"`. Un élément placé hors de l'écran l'est du côté `start` (à gauche, il élargirait la page en hébreu).
- Le gérant répond aux clients en **français, en anglais ou en hébreu** (sa décision, 12 novembre 2026) : ces trois sites annoncent un service dans la langue du client (`accueil.surtitre`), et la page de contact dit partout dans quelles langues on répond. Le russe et l'espagnol ne sont JAMAIS promis (`tests/langues.test.ts`) : ces deux sites disent « nous répondons en anglais, en hébreu ou en français ». Les rayons, le message d'accueil et les modes de paiement de départ sont traduits tant que le gérant ne les a pas changés (`nomDuRayon`, `libelleDuMode`, `MESSAGE_ACCUEIL_PAR_DEFAUT`).
- **Catalogue traduit** : `lib/i18n/catalogue/<langue>.ts` va du texte FRANÇAIS de départ (`prisma/*.ts`) à sa traduction — noms et descriptions d'articles, noms et choix d'options, villes, noms des tarifs. La base ne change pas : elle reste en français, la traduction se fait à l'affichage, côté serveur (`nomArticle`, `descriptionArticle`, `libelleOptions`, `nomVille`, `nomTarif`, `traduireGroupes` dans `lib/i18n/catalogue`). Un texte que le gérant a écrit ou modifié dans l'admin n'est pas dans la table : il s'affiche tel quel. Ces tables sont LOURDES : jamais importées par un composant du navigateur (`"use client"`) — le serveur envoie le résultat (lectures de `lib/catalogue.ts` avec la langue ; `affichage` de la page du panier). Les lignes d'une commande, l'admin, la liste de courses et les exports gardent le français. Options : ce qui est choisi, envoyé et vérifié reste `nom` / `libelle` du gérant ; `affiche` n'est que ce que le client lit (`libelleAffiche`). Recherche : `rechercher(q, langue)` cherche dans le français de la base ET dans sa traduction (voir « Recherche vivante »). **Ajouter un article, une description, une option ou une ville dans `prisma/*.ts` = ajouter sa traduction dans les quatre fichiers** (`tests/catalogue-langues.test.ts` le refuse sinon) : mêmes chiffres que le français, marques inchangées, rien d'ajouté à ce que dit le texte (casher, sans gluten… traduits tels quels).
- **Adresse obligatoire avant la commande** : nom, téléphone, e-mail, ville, où le client loge (`logement` : `APPARTEMENT`, `MAISON` ou `HOTEL` — `lib/adresse.ts`) et la rue ou le nom de l'hôtel (`adresse`) sont exigés par `schemasPour` (`lib/validation.ts`) — rien n'est enregistré ni à payer sans eux. `etage` et `appartement` ne sont exigés que pour un appartement ; une maison n'en a pas ; à l'hôtel le numéro de chambre est facultatif (rangé dans `appartement`) ; `codeEntree` est facultatif. **À l'hôtel, on ne monte pas dans les chambres** (décision du gérant, 12 novembre 2026) : on appelle le client et il descend chercher sa commande — dit au client dès qu'il choisit « Hôtel » (`panier.hotelAvis`), dans les conditions de vente, sur son suivi et dans son e-mail (`adresse.remiseHotel`), dans les messages « en route » et « j'arrive » du gérant (`messages.hotel`), et au livreur (« Ne pas monter », `LIBELLES_ADRESSE_FR`). Une commande d'avant ce choix (`logement` vide) s'affiche comme un appartement. `Commande.adresse` ne porte que la rue ou l'hôtel (Waze) : l'adresse entière s'affiche avec `adresseComplete` / `precisionsAdresse` (`lib/adresse.ts`). `Commande.langue` = la langue du client : son e-mail (`langueDuCourriel`) et les messages WhatsApp du gérant (`langueDesMessages`) sont écrits dans cette langue.
- **Référence de commande** : le client ne lit JAMAIS « n°1 » — le site doit avoir l'air d'une maison installée (demande du gérant, 12 novembre 2026). Partout côté client (suivi, compte, « Mes commandes », e-mails, reçu, messages WhatsApp dans les deux sens) : `referenceDeCommande(numero, nomClient)` (`lib/reference.ts`, pur) → « BC-58001 » = les initiales du client, deux chiffres qui ne comptent pas, puis le numéro à l'endroit, sur trois chiffres au moins (001 → n°1 ; d'abord écrit à l'envers, remis à l'endroit à la demande du gérant le 12 novembre 2026). Les dictionnaires portent `{reference}`, jamais `{numero}` (`tests/reference.test.ts`), et le navigateur ne reçoit pas le numéro (`mesCommandes`). Le gérant voit toujours le numéro ET la référence (liste, commande, e-mail, Telegram) et retrouve une commande par l'un ou l'autre (`numeroDepuisReference`, champ « Retrouver une commande » de `/admin`). Ne pas changer la formule : les références déjà données aux clients ne se reliraient plus.
- Montants en **agorot** (Int). Calcul unique : `lib/calcul.ts`. Le serveur recalcule depuis la base (`lib/commandes.ts`).
- `exigerAdmin()` en tête de chaque page et action de `app/admin/(protege)`.
- Pages publiques : produits lus via `PRODUIT_PUBLIC` (`lib/catalogue.ts`) — jamais `prixAchat`, `boutique`, `lienWolt`.
- Apparence (côté client) : sobre — encre (`bg-encre`), blanc, traits fins, gris neutres (les classes `slate-*` sont remappées dans `@theme`), un seul accent (`marque`, pour les liens et le focus). **Aucun emoji côté client** : icônes au trait de `lucide-react` (`IconeRayon` pour un rayon, d'après son adresse). Un article est une TUILE (`CarteProduit`) : la photo en haut seulement s'il y en a une — jamais d'image de remplacement, la tuile est alors plus basse —, puis le nom, le format, le prix. Deux tuiles par ligne sur téléphone, jusqu'à cinq sur grand écran (`GrilleProduits`), ou une rangée qui défile de côté (`RailProduits`). Avec une photo, le bouton « + » est posé dans son coin haut gauche, DANS TOUTES LES LANGUES — en hébreu aussi, où le reste de la page se retourne (`left-0` : la seule exception à la règle des positions logiques, décidée par le gérant le 12 novembre 2026, « comme sur Wolt »). Couleurs du site : fond `encre`, « + » blanc, et « − n + » à la même place une fois l'article au panier. Sans photo, le bouton est en bas de la tuile, côté fin. Les articles avec photo passent d'abord (`photosDAbord`) : les grandes tuiles se suivent. Arrondis et graisses se règlent dans `@theme` (`--radius-*`, `--font-weight-*`), pas classe par classe. Logo : le sigle (un T et un O plein couleur `soleil` dans une tuile encre) a UN tracé, `lib/sigle.ts`, rendu par `components/Sigle.tsx` (SVG sans classe ni police : il sert aussi aux images générées) ; le jaune `soleil` est réservé à ce O. L'icône de l'onglet et la carte d'aperçu de lien sont générées avec lui (`app/icon.tsx`, `app/apple-icon.tsx`, et `app/apercu/[langue]/route.tsx` : une carte par langue, textes dans `meta.apercu` de `lib/i18n/serveur/` ; polices dans `assets/polices/` — Geist pour le latin et le cyrillique, Heebo pour l'hébreu, dont les lignes sont données retournées car l'outil n'écrit que de gauche à droite), et les fichiers de `public/logo/` portent le même tracé (`tests/logo.test.ts`) : changer le dessin = changer `lib/sigle.ts` ET refaire ces fichiers.
- **Un peu de couleur, sans en abuser** (demande du gérant, 16 novembre 2026, capture de l'accueil à l'appui) — ceci précise la règle d'apparence ci-dessus : le site reste encre, blanc et gris, et la couleur n'entre que par deux portes. (1) Une teinte douce par RAYON (`lib/couleurs-rayons.ts`, `couleurDuRayon(slug)`, reconnue à l'adresse comme l'icône) : elle ne colore que la PASTILLE de l'icône — fond clair `-100`, trait `-800` de la même famille — sur les tuiles de l'accueil, devant le nom de chaque rangée et en tête de la page du rayon ; dans une liste de rayons (colonne, rangée de liens), le trait de l'icône seul. Un rayon créé par le gérant garde le gris (`tests/couleurs-rayons.test.ts` : chaque icône a sa couleur, deux rayons n'ont pas la même). (2) Le jaune `soleil` du logo, qui n'est plus réservé au seul O mais reste rare : les pastilles des repères de livraison (`PASTILLE_SOLEIL`), les numéros de « Comment ça marche », le compteur du panier (en-tête et barre du bas) et la barre de chargement. À ne PAS colorer : un texte, un titre, un prix (sauf la promotion, déjà rose), un bouton (le « + » et « Commander » restent encre — décision du gérant pour le « + »), le fond d'une tuile ou d'une page ; pas d'aplat vif, pas de dégradé. Le vert, l'ambre et le rouge gardent leur sens (ouvert / payé, en attente, refusé). `marque` (bleu) reste la couleur du focus.
- **Fond sombre comme Wolt, couleur sur les pages d'articles** (le même jour, après la première touche : « mets un peu plus de couleur sur les pages produits et un fond de couleur différent — ça fait trop brut et ça ne donne pas envie de commander », puis, captures de Wolt et d'Uber Eats à l'appui : « Wolt a mis un fond noir pour faire ressortir les produits »). Ceci ÉLARGIT la règle précédente. **Le fond de la boutique** se choisit dans `lib/fond.ts` (`FOND_DE_LA_BOUTIQUE` : « nuit », en service, ou « ivoire », clair et chaud — un seul interrupteur) ; le cadre de la boutique le pose dans `data-fond`, et `app/globals.css` redéfinit la variable `fond` (l'espace gérant garde son gris ; à l'impression, le clair). En « nuit » le fond est l'encre du logo : les tuiles et les cartes, blanches, ressortent. Tout ce qui est écrit DIRECTEMENT sur le fond passe en clair avec la variante `nuit:` (`text-encre nuit:text-white`, gris `-600` → `nuit:text-slate-300`, `-500` → `nuit:text-slate-400`, lien → `nuit:text-white nuit:decoration-white/40`) ; elle ne s'applique JAMAIS dans une surface claire (une tuile `article`, une `carte`, une fiche `dialog`, tout élément `bg-white` ou marqué `clair`) : un composant partagé peut la porter sans risque de blanc sur blanc. Ce qui s'assombrit soi-même — l'en-tête, le pied de page, la barre du panier — écrit donc son blanc `bg-[white]`, jamais `bg-white`. Sur le fond sombre : le logo est la tuile claire du sigle (`Logo clair`), le panier de l'en-tête, « Voir le panier » et « Voir les rayons » sont au jaune du logo (texte encre), le rayon ou le sous-rayon ouvert d'une rangée aussi, et l'anneau du clavier est jaune. Les pages de texte (`PageTexte`) sont une feuille blanche. **Tout nouveau texte posé sur le fond doit porter sa classe `nuit:`** — sinon il reste encre sur encre, invisible, sans que rien ne casse : `tests/navigateur/contrastes.mjs` (chaque texte face au fond qu'il a réellement derrière lui, refusé sous 3 ; téléphone, hébreu, ordinateur ; ne modifie rien, se lance aussi sur le vrai site ; `SEULES=1 … /suivi/<jeton>` pour une page du jeu de test). **Pages d'articles** : la tête de la page d'un rayon est un BANDEAU à sa couleur (`couleurDuRayon(slug).bandeau` : fond `-50`, liseré `-200`, l'icône dans un rond blanc) ; un REPÈRE (`.repere`, un petit trait `-400`) précède le titre de chaque sous-rayon (le nom et le nombre d'articles y sont marqués `data-nom` et `data-compte`, lus par `parcours-rayons.mjs`) ; « Tout voir » est une pastille à la couleur du rayon (page du rayon et rangées de l'accueil) ; le PRIX d'une tuile et de la fiche est dans une étiquette au jaune du logo (`Prix etiquette` : `bg-soleil/25`, rose pour une promotion) ; le « + » est plein, encre, sur toutes les tuiles (avec ou sans photo) ; la fiche d'un article sans photo s'ouvre sur un bandeau à la couleur de son rayon (ce n'est pas une image de remplacement : il ne montre pas l'article), et le rayon y est une pastille de couleur. Dans une liste de rayons, le trait de l'icône est clair sur le fond sombre (`trait` : `-700`, `nuit:` `-300`). Restent sans couleur : le fond des tuiles d'articles (blanc), leurs textes, les boutons d'action dans une surface claire (encre). `tests/couleurs-rayons.test.ts`.
- **Mouvement côté client** (demande du gérant, 15 novembre 2026 : « mets-moi un peu plus d'animation, c'est très plat ») : ce qui arrive à l'écran monte en fondu, ce qu'on touche répond — sans sortir du style sobre. Tout est dans `app/globals.css` (classes maison) : `apparait` (arrivée en cascade au chargement, le rang donné par `rangDansLaCascade(i)` de `lib/cascade.ts` ; les 15 premières tuiles d'une grille ou d'une rangée seulement — en animer des centaines ferait peiner un téléphone), `saute` (une quantité ou un compteur de panier qui change : l'élément porte `key={valeur}`), `deploie` (le « − 1 + » se déplie depuis le « + »), `monte` (la barre du panier), `entree-page` (fondu du contenu à chaque changement de page, `components/EntreePage.tsx` : il relance l'animation sans rien remonter — pas de `template.tsx`, qui viderait un formulaire en cours). Un bloc plus bas dans la page passe par `components/Apparition.tsx`. Règles à garder : (1) RIEN n'est caché par la feuille de style ni par le serveur — `a-venir` n'est posé que par le navigateur, sur un bloc encore sous l'écran ; sans JavaScript, pour un moteur de recherche et à l'impression, toute la page est là ; (2) une animation ne laisse rien derrière elle (`backwards`, jamais `forwards`) ; (3) le contenu d'une page ne se DÉPLACE jamais en bloc (fondu seulement) : un bloc déplacé décrocherait ce qui reste collé à l'écran (rangée des sous-rayons, barre du panier) ; (4) tout est coupé pour qui a demandé moins d'animations à son appareil (`prefers-reduced-motion`) ; (5) une zone annoncée aux lecteurs d'écran (`aria-live`) ne porte pas la `key` — c'est son contenu qui la porte ; (6) le survol (tuile qui se soulève, photo qui grossit) n'existe que sur ordinateur : sur téléphone, ce qui compte est l'arrivée des blocs et la réponse au toucher. Vérifier : `tests/navigateur/mouvement.mjs` (français et hébreu, sans JavaScript, animations réduites, ordinateur), sur le catalogue entier.
- **Mouvement, suite** (le même jour : « mets-en plus sur le panier, la page de suivi et sur tout le site ») — mêmes règles, autres classes de `app/globals.css` : `change` (un montant ou un état qui change revient en fondu : `key={valeur}` — `RecapMontants`, prix d'une ligne, état d'une commande), `balance` (le chariot de l'en-tête), `tourne` (attente : bouton « Commander », globe des langues), `se-remplit` (barre d'avancement d'une commande), `se-trace` (la coche du remerciement et de « paiement reçu »), `en-fondu`, `bat` (un halo en boucle — réservé à ce qui ATTEND le client : l'étape en cours d'une commande non livrée et le bouton de paiement de la page de suivi ; rien d'autre ne boucle sur le site, à part `tourne` pendant un envoi). Un choix coché (`pastille`) répond d'un appui, un champ refusé (`champ-erreur`) se secoue une fois. Panier (`PageDuPanier.tsx`) : les lignes arrivent en cascade, une ligne retirée se replie avant de quitter le panier (`retirer` : 220 ms, la rangée de sa grille passe de 1fr à 0fr), les étapes 2 à 5 passent par `Apparition`, les champs du logement choisi arrivent en montant — le récapitulatif collé à l'écran (`lg:sticky`) n'est JAMAIS enveloppé dans un bloc de sa hauteur (il ne serait plus collé). En-tête : `components/CadreEnTete.tsx` (ombre dès qu'on fait défiler), `logo-vivant` (le O du sigle rebondit à l'ouverture ; le SVG de `Sigle` reste sans classe). `components/BarreDeNavigation.tsx` : la fine barre en haut de l'écran pendant qu'une page se charge (part au toucher d'un lien du site ou à l'envoi de la recherche ; décorative, se retire seule ; dans un `<Suspense>`). Deux pièges rencontrés : deux éléments voisins ne portent jamais la même `key` (le chariot et son compteur, tous deux `key={nombre}` : React en laissait des copies dans l'en-tête) ; un `setState` ne s'écrit pas directement dans un effet (règle `react-hooks/set-state-in-effect`) — dériver l'état, ou le poser dans une minuterie. Vérifier : `mouvement.mjs` (ne modifie rien : se lance aussi sur le vrai site) et `tests/navigateur/mouvement-commande.mjs` (passe une commande : jeu de test local seulement, sur un serveur fraîchement démarré — le site limite le nombre de commandes par visiteur, et après plusieurs parcours enchaînés le formulaire ne répond plus par des champs refusés).
- **Mouvement, articles et accueil** (16 novembre 2026 : « on continue avec les produits et la page d'accueil ») — toujours les mêmes règles. Articles : au « + », l'article s'envole vers le panier (`lib/envol.ts`, `envolVersLePanier` : une pastille — sa photo, sinon un rond encre — part de l'endroit touché vers `data-cible-panier`, la barre du bas sur téléphone, le panier de l'en-tête sinon ; décoratif, rien n'en dépend, elle se retire toujours) ; depuis la fiche produit, l'envol part APRÈS sa fermeture (un élément posé dans la page reste sous une boîte de dialogue ouverte). Photos : `components/Photo.tsx` — une photo qui charge encore quand la page devient active reste transparente puis arrive en fondu ; l'état (`data-chargee`) est posé par le navigateur sur l'élément, jamais par le serveur ni la feuille de style seule. Fiche produit : elle se referme en redescendant (`fermerEnDouceur`, `data-se-ferme` ; la touche Échap passe par `onCancel`). Longue liste (sous-rayon entier, petit rayon, recherche) : `GrilleProduits auDefilement` — les tuiles encore sous l'écran arrivent rangée par rangée en faisant défiler, avec UN observateur pour la grille (`useTuilesAuDefilement` ; les classes sont posées sur les éléments, que React ne réécrit pas tant que leur `className` ne change pas) ; elles arrivent dès qu'elles touchent le bas de l'écran et vite (`vite`) : après un coup de pouce, l'écran ne reste jamais vide (une première version, plus lente et en cascade sur tout le lot, laissait un écran blanc). Les aperçus de sous-rayons, eux, restent des blocs d'`Apparition`. Accueil : le titre arrive mot à mot (chaque mot est un `span` ; le texte lu ne change pas), un point vert qui bat sur la prochaine livraison quand les commandes sont ouvertes (`PointOuvert` : `reglages.ouvert` et un créneau à venir — la troisième et dernière chose qui boucle avec `bat`), les icônes des rayons rebondissent après l'arrivée de leur tuile, et dans une rangée qui défile de côté les tuiles arrivent de côté (`glissade`, vers la gauche en hébreu). Un bloc ou une tuile en attente coupe l'animation de ce qu'il contient (`.a-venir .apparait`, `.a-venir.apparait` : `!important`, plus fort que les règles de rangée). Vérifier : `mouvement.mjs` (109 vérifications, aussi sur le vrai site). Les parcours qui passent des commandes s'enchaînent mal sur un même serveur local (limite de commandes par visiteur) : redémarrer le serveur entre deux séries.
- **Logo animé, en-tête qui respire** (16 novembre 2026 : « une animation avec le logo et faire respirer le header »). Logo : `Logo vivant` (l'en-tête de la boutique seulement ; le pied de page et l'espace gérant gardent un logo immobile) — à l'ouverture du site la tuile se pose, le T descend, le O (le soleil de la marque) se lève du bas de la tuile ; pendant qu'une page se charge, le O bat (`html[data-page-en-route]`, posé par `BarreDeNavigation`).
